# CLI capability matrix

This matrix maps meaningful application work in the desktop UI to its finite CLI operation/query and the result an automation caller can observe. Decorative UI gestures are excluded; application effects, readiness, transaction outcomes, and required human actions are not.

CLI commands use the syntax in [Command-line control](cli.md). JSON output is always enabled. Read `capabilities` and `settings choices` on the live host for dynamic setting names, provider/model/connection values, local-device values, overlay presets, and loaded HTTP-extension secret declarations; this matrix intentionally does not duplicate those variable catalogs.

| GUI function or application workflow | CLI action / query | Observable result and boundary |
| --- | --- | --- |
| Start without the main GUI | `app start --foreground` or `app start --background`; direct host: `run-headless --config FILE` | Explicit ready/start result and instance ID. Background service outlives its short-lived launcher; duplicate canonical settings ownership is rejected. |
| Discover, inspect, restart, and stop an instance | `app list`, `app discover`, `app status`, `app restart`, `app stop [--no-wait]` | Per-user instance identity, host PID observation, selected/runtime channel snapshot, translation/output state, stopping state. Waited stop confirms the original instance endpoint and process identity both ended. |
| General settings and available controls | `settings current`, `settings choices`, `capabilities`; queries `settings.current`, `settings.choices` | Canonical persisted intent and revision are separate from dynamic choices. Unknown fields/types and stale expected revisions are rejected. |
| Self microphone/STT enable and disable | `capture set self on\|off`; `capture status`; query `capture.channels` | Receipt and self channel snapshot with desired/effective activity, selected/runtime/capture-attached provider, provider readiness, pending handoff, and failure reason. |
| Peer/other-speaker capture enable and disable | First inspect `capture terms` or query `consent.peer_translation`, then an explicit `capture set peer on --accept-peer-terms`; disable with `capture set peer off`; inspect `capture status` | The query returns current consent plus the exact localized terms. The acceptance flag is an explicit user action and routes through the existing GUI application acceptance owner; it must not be sent by automation without the user's informed choice. Without previously accepted terms or explicit acceptance, enable returns `action_required` and capture stays off. No consent is auto-accepted. |
| Translation enable and disable | `translation set on\|off`; query `app.status` | Explicit enabled state, runtime readiness, and terminal action-required/degraded result when authorization or runtime prerequisites are absent. This command and OSC translation input do not initiate OAuth. |
| Manual text submission | `text submit --file FILE` or `text submit --stdin` | Non-empty text enters the normal self transcript → translation turn → self output path. It bypasses microphone capture/STT. Peer output remains excluded from the VRChat chatbox. Text is protected content, never a regular process argument. |
| Microphone test | `microphone test on\|off`; `app status` | The `microphone_test` snapshot exposes pending/ready/failed/off state, desired/effective activity, normalized meter level, and failure reason/type. Start waits for a real input frame; unavailable input is action-required. Stop interrupts pending startup and completes after owned resources close. No audio content is exposed. |
| Same ASR provider for self, peer, or both | `asr set --channel self\|peer\|both --provider VALUE`; query `providers.status` / `asr status` | Terminal result plus per-channel selected provider, active runtime provider, capture-attached provider, pending handoff, desired/effective activity, readiness/failure. `both` is one requested provider-apply operation. |
| Different ASR providers on the two channels | `settings apply --file FILE --expected-revision N`, with `stt.provider` and `peer_stt.provider` in one `changes` object; or finite command `provider.apply` with separate `self` and `peer` values | One settings/provider application result with revision and transaction diagnostics. Each active channel must be checked for matching selected/runtime/attached provider; a handoff or mismatch is not full success. |
| ASR provider selection and free-tier configuration | `settings apply` fields `stt.provider`, `peer_stt.provider`, `stt.cloud_free_tier_providers`; inspect `settings choices`, `providers.status` | Values are validated against supported providers and the free-tier allowlist. Configured provider selections are distinct from attached/effective runtime state. |
| ASR and translation GPU device selection | `settings apply` fields `stt.gpu_device_id`, `translation.gpu_device_id`; `gpu status`, `gpu discover` | GPU discovery/runtime snapshot and selected device IDs. Missing device/model/runtime effects produce a truthful failed/degraded result, not an applied claim. |
| Qwen region and model/connection choice | `settings apply` fields `translation.qwen.region`, `translation.model`, `translation.connection`, `translation.connection_history`, `translation.previous_llm_model`; `settings choices`, `settings current` | Region and supported model/connection combinations are runtime-discovered and validated. Selection/configuration is not proof that a provider credential or model is ready. |
| Additional provider/account settings | `settings apply` fields `stt.soniox.enable_speaker_diarization` and `managed.referral_id`; consult `capabilities`/`settings choices` for field types and allowed values | Typed provider/account changes are applied through the existing settings owners. Referral values remain configured intent, not proof of authentication or runtime readiness. |
| Credential-source selection for translation providers | Typed `translation.model` / `translation.connection` updates using the current allowed settings choices; `settings current`, `providers.status`, `auth status`, `secrets presence` | The configured model/connection/profile and managed-account or stored-key presence are observable separately from secret values and runtime readiness. Never infer that a selected source is authorized solely from configuration. |
| Custom ASR provider settings | `settings apply` fields `stt.custom.endpoint`, `stt.custom.model`, `stt.custom.extra_json`; provider selection via `stt.provider` or `peer_stt.provider` | Typed provider transaction and channel runtime snapshot. Endpoint/model are ordinary settings; secrets remain in the secret store. |
| Custom/local translation provider and HTTP extension selection | `settings apply` fields `local_llm.base_url`, `local_llm.model`, `local_llm.extra_body_json`, `translation.http_extension_id`, `translation.model`, `translation.connection` | Typed transaction and current settings/runtime outputs. Extension identifiers and compatible model/connection choices come from runtime capabilities/choices. Sensitive custom HTTP body keys must not be populated with secrets. |
| Provider API credential storage and deletion | `secrets set NAME [--stdin]`, `secrets delete NAME`, `secrets presence` | Secret-store write/delete transaction and boolean presence by declared key. No secret value is returned. Loaded, declared HTTP-extension secrets are included in the capability and presence key lists. |
| API credential verification | `secrets verify NAME [--stdin]` | Verification is separate from storage; supported provider key types return verified/rejected state. Custom or extension-declared keys without a verification protocol return terminal `action_required` / `verification: unavailable`, never fake success. This is not a live validation probe until a user explicitly runs it. |
| UI locale, languages and source/target language modes | `settings apply` fields `locale`, `languages` (partial object with source, target, secondary_target, peer_source, peer_target, peer_source_mode), and `peer_expected_languages`; `settings current` and `settings choices` | Typed locale/language selection is applied through existing settings/language owners; available locales, language codes, and modes come from current choices. Current settings are not an active-transcription proof. |
| Prompts and custom vocabulary | `settings apply` fields `prompts.value`, `prompts.system_prompt_override`, and `custom_vocabulary` (`source_language`, `terms`) | Typed prompt/vocabulary settings outcome. Prompt and vocabulary contents are redacted from default query/log projections; use protected JSON files rather than process arguments. |
| Self/peer VAD tuning | `settings apply` fields `self_vad.speech_threshold`, `peer_vad.speech_threshold`, `peer_vad.hangover_ms`, `peer_vad.pre_roll_ms` | Type/range validation and settings transaction outcome; peer/self capture owner status remains the effective runtime view. |
| Clipboard, chatbox, and microphone interception settings | `settings apply` fields `clipboard.enabled`, `chatbox.source.enabled`, `vrc_mic_intercept.enabled` | Persisted/applied settings transaction. Effective output and capture behavior remains visible through application/channel/output state; peer speech is never routed to the VRChat chatbox. |
| OSC configuration and runtime connection | `settings apply` field `osc.connection` (`mode`, `receive_port`, optional `send_port`); `osc status` | The top-level `output` object from `osc status` reports `configured_mode`, `configured_host`, `configured_send_port`, `configured_receive_port` separately from `effective_mode`, `effective_send_port`, `effective_receive_port` (each `null` without its runtime resource). It also exposes `receiver_available`, `sender_available`, `query_service_started`, `query_advertised_port`, `discovered_remote` (`host`, `send_port`), `query_failure` type, and `local_availability` (`off`, `closed`, `receiver_unavailable`, `sender_unavailable`, `starting`, `available`). `remote_delivery` is always `unacknowledged`; UDP status does not claim VRChat acknowledgement. OSC translation commands still do not initiate OAuth. |
| Telemetry preference | `settings apply` field `telemetry.enabled`; `settings current` | Typed settings result and current preference. This does not expose conversation content or credentials. |
| Input microphones and host APIs | `audio devices list`; `settings apply` fields `audio.input_host_api`, `audio.input_device` | Device/host-API options plus selected/effective device listing. Missing devices or desktop-session access are explicit states; listing does not start capture. |
| Output device | `audio devices list`; `settings apply` field `audio.output_device` | Available output devices and typed selection transaction. Effective routing remains an application/runtime state, not merely a saved ID. |
| Loopback/process target selection | `audio processes list`, `audio target status`, `audio target set VALUE` | Options, selected target, effective capture summary and operation result. Target identifiers must be read from the current option list, not guessed. |
| Lost process-target recovery | `audio retry` | Explicit peer process-capture retry and truthful target/runtime result; unavailable process/desktop target does not count as successful capture. |
| CPU and GPU ASR model readiness/integrity | `models status`; `models prepare --backend cpu\|gpu [--verify-checksums]`; `gpu status` | Model provisioning snapshots report readiness/integrity and GPU discovery/activation state. GPU preparation is explicit intent. |
| CPU/GPU model install, repair, and reinstall workflow | `models install --backend cpu\|gpu [--model-id ID ...]`; inspect `models status` and operation status/events | Progress and terminal result are owned by the model provisioning owner; failed model IDs, cancellation, or degradation remain visible. Model IDs come from the live provisioning snapshot and must match the requested backend. The GUI's GPU install/repair/reinstall labels all use this same owner install/repair validation procedure exposed as `models.install`; a sound installed asset is reused rather than force-redownloaded. |
| Model install cancellation and backend retry | `models cancel --backend cpu\|gpu`; `models retry --backend gpu` for GPU activation; `models install --backend cpu\|gpu` for provisioning install/repair retry; `operation cancel ID` for supported install operation | Only an active supported installation is cancellable; no active install is a rejected result. GPU activation retry reports discovery/activation failure honestly. CPU recovery re-enters the CPU provisioning repair/install owner. Cancellation does not undo already committed/applied changes. |
| Managed local Gemma readiness, preparation, cancellation | `models status`; `gemma prepare`; `gemma cancel`; `operation status\|wait\|cancel ID` | Gemma owner snapshot and asynchronous preparation outcome. Preparation is an explicit local model action, not automatic authorization. Cancellation is supported only while that owned operation remains cancellable. |
| Fixed-provider, regional, managed, BYOK, local, custom, and declared HTTP-extension credentials | `capabilities`, `secrets presence`, `secrets set/delete/verify`, `auth status` | Fixed and region-specific secret identifiers and loaded extension declarations come from the host. Set/delete state is separate from verification and account login. Secrets remain hidden/redacted. Unsupported custom verification is action-required. |
| QQ account login, authorization progress, and logout | `auth login qq` (hidden prompts) or `auth login qq --stdin`; `auth status`; `auth logout qq`; operation commands | QQ identity/credential are protected input. Login result/action-required is explicit; logout is local state removal and may require resolving a pending managed authorization. Credentials are not returned. |
| Discord account login, authorization progress, explicit browser, logout | `auth login discord [--stdin] [--open-browser]`; `auth status`; `events follow --topic auth`; `auth logout discord`; operation commands | Human authorization URL and auth progress are available only after an explicit login or explicit auth observation. Browser launch requires `--open-browser`; account logout is local and does not revoke remote access. Active login cancellation is not claimed when unsupported. |
| OpenRouter login, authorization progress, explicit browser, logout | `auth login openrouter [--stdin] [--open-browser]`; `auth status`; auth events/operation commands; `auth logout openrouter` | Explicit PKCE challenge can require human browser action; no verifier or credential is returned. `--open-browser` is the sole CLI browser admission. Logout removes local authorization/key state, not remote grants. Active login cancellation is not claimed when unsupported. |
| Overlay enablement, selected target, and runtime lifecycle | `overlay set on\|off`; `settings apply` field `overlay.target`; `overlay status`; `app status` | The top-level `output` object from `overlay status` exposes `settings_available`, `desired_enabled`, `configured_target`, `effective_target`, `attempting_target`, `ingress_stopped`, `lifecycle`, `runtime_active`, `process_state`, `presentation_ready`, `generation`, `failure_reason`, `auto_restart_scheduled`, `fallback_active`, `recovery_active`, and `recovery_reason`. `effective_target` is reported only when connected/manager handshake/presenter applies; it is not inferred from configured target. `overlay set` receipts become terminal after the owner transition reaches its outcome; pending startup/recovery is not reported as applied. |
| Overlay position/size, alpha, caption swap, lock, and reset | `overlay size PRESET`, `overlay lock on\|off`, `overlay reset-position`; `settings apply` fields `overlay.desktop_size`, `overlay.background_alpha`, `overlay.swap_caption_languages` | Typed settings and lock/target state; size presets come from `settings choices`. `desktop_visible` is separate from `presentation_ready` and is `null` for non-desktop targets. |
| Overlay calibration and draft/effective output | `overlay calibrate begin`; `overlay calibrate change --field anchor --value VALUE` or `overlay calibrate change --field offset_x\|offset_y\|distance\|text_scale\|background_alpha --value NUMBER`; then `apply` or `cancel`; `overlay status` | `anchor` is a string choice from the `overlay.calibration_fields.anchor` entry in the `settings choices` response. The other fields accept finite numeric values; `distance` and `text_scale` must be greater than zero, and `background_alpha` must be from 0 through 1. Status reports `output.calibration_draft_active`, target generation, presentation readiness, process state and failure/recovery state, separate from configured settings. |
| Translation overlay and original-peer output | `settings apply` fields `overlay.translation.enabled`, `overlay.peer_original.enabled`; `overlay status`, `app.status` | Typed destination settings plus desired/effective output and presentation state. `desktop_visible` is `null` for non-desktop targets. UDP `remote_delivery` is unacknowledged; peer output remains excluded from the VRChat chatbox. |
| Channel/application state and operation outcomes | `app status`, `capture status`, `asr status`, `operation status\|wait ID` | Owner-derived snapshots/receipts, not UI-widget state or log parsing. Selected provider, runtime provider, capture attachment, desired/effective activity, handoff, and failure are distinct values. |
| State, recognition, translation, auth, operation, and error event streams | `events follow [--topic TOPIC ...] [--channel self\|peer] [--after N]`; add content flags only when needed | Independent buffered subscription with sequence IDs, explicit gap/snapshot-required marker, and resynchronization through snapshots. Topics/content inclusion must be selected; no global order is promised across channels. |
| Logs and diagnostics | `logs follow --level debug\|info\|warning\|error` | Bounded, application-sanitized metadata; warning is the default threshold. No credentials or transcript/translation bodies are included. Logs are not an authoritative operation ledger. |
| Slow clients, disconnects, and uncertain delivery | `operation status\|wait ID`, then inspect `app status`/relevant domain snapshot | Client loss never silently cancels accepted work. Ambiguous transport outcome is `unknown_execution`; callers must not blindly resubmit. Host-local request/operation retention is bounded to 256 identities and ends at host restart. |

## Typed settings payload examples

Provider change for both channels in one explicit application intent:

```json
{
  "changes": {
    "stt.provider": "soniox",
    "peer_stt.provider": "qwen_audio"
  }
}
```

Focused updates can be applied from a UTF-8 file against the current settings revision. The caller reads the current revision first; the example revision below is illustrative only:

```powershell
puripuly.exe settings current
puripuly.exe settings apply --file .\changes.json --expected-revision 12
```

A typed settings file may include adjacent unrelated choices because the application owner materializes focused changes onto the latest canonical settings. Invalid fields, stale revisions, persistence failure, and persisted-but-runtime-degraded outcomes are reported distinctly. Do not treat a successful settings write as evidence of effective capture/provider state.

## Coverage gaps and evidence boundary

The peer-consent interaction now has a CLI route because an authorized CLI caller can retrieve the terms and explicitly pass `--accept-peer-terms`; this is a deliberate consent act, not automatic acceptance. The required user-facing text must be inspected before setting that flag. Never run that flag as a documentation smoke test.

The matrix documents available implemented command/query surfaces. It does not claim all issue #193 completion criteria or installed-build, real audio, account, GPU/model, or desktop-session evidence have passed. Those observations belong in the issue's evidence record.
